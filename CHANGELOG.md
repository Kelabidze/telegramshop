# CHANGELOG

История изменений проекта. Формат основан на
[Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии — по
[SemVer](https://semver.org/lang/ru/).

## Правила ведения (для ИИ и людей)

- Каждая задача, меняющая код, добавляет запись в `[Unreleased]`.
- Пиши **что изменилось для проекта**, а не «поправил файл X». Плохо:
  «изменён orders.ts». Хорошо: «заказ больше не создаётся при нулевом остатке».
- Категории: `Добавлено`, `Изменено`, `Исправлено`, `Безопасность`,
  `Удалено`, `Устарело`. Пустые категории не создавай.
- Изменения, затрагивающие инварианты безопасности из `AGENTS.md`, всегда
  идут в `Безопасность` — даже если это рефакторинг.
- Одна строка = одно изменение. Ссылайся на файлы в формате
  `apps/api/src/services/orders.ts` там, где это помогает.
- Ломающие изменения помечай `**BREAKING:**` в начале строки.
- При выпуске версии: переименуй `[Unreleased]` в `[x.y.z] — YYYY-MM-DD`
  и создай новый пустой `[Unreleased]` сверху.

## [Unreleased]

### Исправлено

- **Корзина больше не роняет всё приложение в чёрный экран.** `selectTotals`
  строил новый объект на каждый вызов, а Zustand сравнивает результат селектора
  по ссылке — стор считался изменённым, начинался бесконечный ререндер, и React
  снимал всё дерево. Итог: чёрный экран во всём Mini App, не только в корзине.
  Заменено на `cartTotalsFor(lines, isSubscribedChannel)` — обычную функцию от
  уже подписанного `lines`. Правило записано в `docs/ARCHITECTURE.md`: производные
  объекты в селекторе Zustand либо мемоизируй, либо не считай там вовсе.
- **Возврат «Назад» больше не выбрасывает в начало списка.** Позиция прокрутки
  запоминается на экран и на фильтр (`hooks/useScrollRestoration.ts`) и
  восстанавливается при возврате из карточки товара. Экраны при навигации
  размонтируются, поэтому позиция живёт в module-level `Map`, а не в state, и
  применяется через два кадра: до layout документ ещё короткий и `scrollTo` не
  доезжает. Тап по активной вкладке возвращает наверх — иначе восстановленный
  скролл стал бы ловушкой без способа подняться.

### Добавлено

- **В профиле — «Ты с нами N дней!»** вместо строки с ролью. Считается от
  `createdAt` пользователя, который теперь приходит в `/api/me`: клиентские часы
  для такого счёта не годятся. Округление вниз (пришедший минуту назад видит 0, а
  не «1 день»), склонение через `pluralDays` с корректными 11–14, отрицательные
  значения при расхождении часов зажаты в 0.
- **Роль видна только персоналу.** `ADMIN` и `MANAGER` — да, покупателю строка
  «Покупатель» ничего не сообщала и убрана.
- **Переименование в магазине** — сворачиваемая панель в профиле и
  `PATCH /api/me` (`services/profile.ts`). Имя лежит в отдельной колонке
  `User.displayName`, а не в `firstName`: `upsertUser` перезаписывает поля
  Telegram на каждом запросе, и своё имя пропало бы при следующем открытии.
  `null` сбрасывает обратно к имени из Telegram. Валидация — общая схема
  `displayNameSchema`, поэтому сообщение об ошибке совпадает с правилом, которое
  реально применит сервер. Эндпоинт действует только на подписавшего запрос: ни
  в пути, ни в теле нет id, и это закреплено тестом.
- Новое имя сразу видно в шапке: мутация пишет ответ прямо в кеш `['me']`,
  который читает `AppLayout`, — без ожидания рефетча.
- **Ссылка на канал приходит с сервера** (`viewer.clubChannelUrl`) вместо
  вкомпилированной `VITE_CLUB_CHANNEL_URL`. Ссылка обязана указывать на тот же
  канал, членство в котором проверяет этот сервер, а копия в бандле расходится с
  ним при смене канала. Build-переменная осталась только как fallback.
- **Кнопка «Все товары ✕»** рядом с заголовком списка сбрасывает выбранную
  категорию. Показывается только при активном фильтре: постоянная кнопка над
  неотфильтрованным списком ничего не делает. Тап по активной плитке по-прежнему
  снимает фильтр.

### Безопасность

- **Роль `ADMIN` снова выдаётся и отзывается только через `ADMIN_TELEGRAM_IDS`.**
  Когда авторизация переехала с `isAdmin` на `role`, реализовали лишь половину
  логики — повышение. Удаление Telegram ID из `ADMIN_TELEGRAM_IDS` оставляло в
  таблице запись `role = "ADMIN"`, и пользователь сохранял полный доступ после
  перезапуска сервиса: отобрать права можно было только правкой БД руками.
  Проверено эмпирически до фикса: `ADMIN_TELEGRAM_IDS=""` → `role` остаётся
  `ADMIN`, защищённый роут отвечает 200. Это нарушало инвариант из
  `docs/ARCHITECTURE.md` («права выдаются и отзываются без правки БД») — самый
  опасный вид регрессии, потому что отзыв доступа обычно нужен срочно.
  Теперь `resolveRole()` работает в обе стороны: id есть в конфиге → `ADMIN`,
  id нет → `USER`. Роль `ADMIN`, выставленная в базе напрямую, сбрасывается при
  первом же входе. `MANAGER` конфигом не управляется и не затрагивается.
- **Понижение менеджера отзывает доступ, даже если строки прав остались.**
  `requirePermission` проверяет не только наличие права, но и роль: у `USER`
  забытые строки `ManagerPermission` больше ничего не открывают.
- **Неизвестные права из БД отбрасываются.** `Viewer.permissions` валидируется
  по `permissionSchema`, поэтому право, удалённое из кода, перестаёт действовать
  сразу и не «протекает» наружу как нераспознанная строка.
- **Опечатка в `requirePermission` больше не превращается в тихий 403.** Права
  описаны закрытым zod-enum, а аргумент проверяется при регистрации роута:
  `requirePermission('EDIT_CATALGO')` роняет старт сервера с внятным
  сообщением. Раньше такой guard компилировался, деплоился и отказывал всем —
  внешне неотличимо от честного запрета.

### Исправлено

- **Проверка членства в канале больше не молчит.** Раньше любой HTTP 400 от
  `getChatMember` — и «user not found» (обычный неподписчик), и «chat not found»
  (неверный `CLUB_CHANNEL_ID`) — глотался без единой строки в логе. Опечатка в
  id канала выглядела в точности как «проверку никто не вызывает». Теперь
  «chat not found» / `CHAT_ID_INVALID` / `PEER_ID_INVALID` пишутся в journal один
  раз за жизнь процесса, с самим id; «user not found» по-прежнему тих — это
  штатный ответ. То же для 403 (бот не администратор канала).
- Ранний выход «канал не настроен» / «нет токена бота» тоже логируется один раз:
  иначе выключенная фича неотличима от работающей, которая просто никого не
  находит. Раньше `if (!enabled || !bot) return false` уходил без следа.
- `/health` теперь отдаёт `clubChannelConfigured: boolean` — достаточно, чтобы
  отличить «фича выключена» от «Telegram отказал», не раскрывая сам id.
- При старте процесс один раз пишет в journal либо
  `Club channel membership checks enabled` с id и TTL, либо warn, что канал не
  настроен. Без этой строки отсутствие скидки диагностировалось по жалобам, а не
  по логам.

### Добавлено

- **Клубный тариф заработал целиком: проверка подписки и расчёт цены.**
  `Viewer.isSubscribedChannel` больше не константа — членство проверяется
  методом `getChatMember` (`apps/api/src/telegram/membership.ts`), а
  `createOrder` считает сумму через `effectiveUnitMinor`. Витрина, карточка,
  корзина и инвойс Telegram теперь показывают одно и то же число: и клиент, и
  сервер зовут одну функцию из `packages/shared/src/pricing.ts`.
- **Ответ `getChatMember` кешируется в памяти** на `CLUB_MEMBERSHIP_TTL_SECONDS`
  (по умолчанию 60 сек). Без кеша каждый `/api/me` и каждое оформление заказа
  били бы в Bot API, у которого есть лимиты и задержка больше, чем у запроса к
  БД рядом. Redis не заведён намеренно: значение живёт минуту и дешевле
  пересчитывается, чем хранится.
- **TTL асимметричный: отрицательный ответ живёт вчетверо меньше положительного.**
  Дорогая ошибка — закешировать «не подписан» тому, кто только что подписался: он
  увидит предложение, вступит в канал, вернётся — и всё равно заплатит полную
  цену. Это читается как «магазин меня игнорирует». Передержать «подписан»
  можно: это всегда в пользу покупателя.
- **Кнопка «Я подписался!» сбрасывает кеш.** Бот добавляет к URL Mini App
  параметр `club_check`, клиент превращает его в заголовок `x-club-recheck: 1`, а
  сервер по нему делает свежий запрос вместо ответа из кеша. Заголовок — только
  подсказка: ответ всегда даёт `getChatMember`, поэтому подделка даёт лишь лишний
  запрос, а не скидку. Закреплено тестом.
- Использовать `start_param` Telegram для этого сигнала нельзя: он заполняется
  только для прямых ссылок `t.me/bot/app?startapp=` и меню вложений, но **не** для
  inline-кнопки `web_app`. Реализация на `initData.start_param` собралась бы,
  задеплоилась и никогда не сработала.
- **Проверка членства идёт параллельно с `upsert` пользователя** (`Promise.all`
  в `plugins/auth.ts`): это сетевой вызов к Telegram и локальная запись, друг от
  друга они не зависят. Последовательный вариант добавлял бы round-trip к Bot API
  в задержку каждого авторизованного запроса.
- **Новый обработчик `/start`** (`apps/api/src/routes/bot.ts`): текст от лица
  Фина с прямой ссылкой на канал и inline-клавиатура из двух кнопок, обе
  открывают Mini App — «Я подписался!» (с пересчётом статуса) и «Продолжить без
  скидки в 5%». Одной кнопки не хватило бы: она либо никогда не обновляла бы
  клубный статус, либо загоняла всех в канал.
- `PUBLIC_APP_URL` — публичный origin Mini App для кнопок бота. Раньше кнопка
  открывала `PUBLIC_API_URL`, то есть API: в production это тот же домен, а в
  dev пользователь получил бы JSON 404 вместо магазина.
- `CLUB_CHANNEL_ID`, `CLUB_CHANNEL_URL`, `CLUB_MEMBERSHIP_TTL_SECONDS` в конфиге
  API. `CLUB_CHANNEL_ID` и `CLUB_CHANNEL_URL` обязаны быть заданы **вместе** —
  иначе половина механики отваливается молча: либо подписчикам обещан тариф, в
  канал за которым никого не приглашают, либо приложение зовёт в канал, членство
  в котором никогда не проверяется. `config.ts` падает при старте на такой
  конфигурации.
- Тесты: `apps/api/src/telegram/membership.test.ts` (9 тестов на заглушке Bot API
  по loopback — статусы, кеш, сброс, поведение при сбоях) и проверка в
  `server.test.ts`, что подписчик платит цену из БД, а неподписчик — стандартную.

### Изменено

- **`Price` принимает клубный тариф и флаг подписки, а не готовую сумму**
  (`components/ui.tsx`). `isSubscribedChannel` — обязательный проп: место
  вызова, забывшее про клубную цену, теперь не компилируется, вместо того чтобы
  тихо нарисовать число, которое опровергнет инвойс. `compareAtMinor`
  пересчитывается тем же способом — иначе «старая» цена у неподписчика могла
  оказаться ниже текущей и превратить скидку в подорожание.
- **Корзина считает итог на рендере, а не хранит его.** `selectTotalMinor`
  заменён на `selectTotals(isSubscribedChannel)`: `unitAmountMinor` в
  localStorage — это клубный тариф из каталога, а статус подписки может
  измениться, пока товары лежат в корзине. Теперь подписка обновляет сумму на
  следующем кадре.
- Тексты в UI переведены на слово «скидка», как просит продукт: в профиле —
  «Подпишитесь на наш канал, чтобы получать скидку в 5% на все товары по
  клубному тарифу», в модальном окне карточки — «Подпишитесь на наш канал для
  скидки 5% по клубному тарифу!». В обоих местах рядом кликабельная ссылка на
  канал. В коде запрет на слово `discount` сохраняется.
- Плашка в корзине называет сумму, а не процент («Вы можете сохранить 120 ⭐»):
  «сохранить 5%» — это домашнее задание по арифметике, а не аргумент. Если
  выгода округляется в ноль (товар за 1 звезду), текст возвращается к проценту.
- В `deploy/setup-server.sh` и `.github/workflows/deploy.yml` добавлены новые
  переменные. `VITE_CLUB_CHANNEL_URL` задаётся **на шаге сборки**: Vite
  подставляет env в бандл на этапе build, и переменная, добавленная после,
  оставила бы приложение без ссылки на канал при работающей проверке членства.

### Безопасность

- **Проверка членства падает «закрыто».** Недоступный Bot API, отсутствие у бота
  прав администратора канала, неверный id — всё это даёт «не подписан», а не
  исключение и не скидку всем. `isClubChannelMember` не бросает вообще:
  исключение уронило бы `/api/me`, то есть весь каркас приложения, вместе с
  Telegram. Обратный вариант (падать «открыто») хуже: одна сетевая икота выдавала
  бы пониженную цену всем подряд.
- Сбой транспорта, в отличие от ответа Telegram, **не кешируется**: иначе
  секундная сетевая проблема держала бы подписчика на полной цене весь TTL.
- Статус `restricted` не считается членством: пользователь известен каналу, но в
  нём не состоит, и выдавать клубную цену забаненному — не то, что имелось в
  виду. Покрыто тестом.
- Цена по-прежнему берётся только из БД. Флаг подписки — серверный, из
  `getChatMember`; клиент не может ни прислать его, ни повлиять на него.

- **Единый корневой каркас интерфейса `AppLayout`**
  (`apps/miniapp/src/components/AppLayout.tsx`): верхний блок профиля (аватар из
  инициала + имя) и нижняя панель навигации теперь живут в обёртке, а не внутри
  экранов. Раньше `TabBar` рендерился в `App.tsx`, а приветствие — внутри
  `CatalogScreen`, из-за чего шапка исчезала в корзине и заказах. Обе панели
  монтируются один раз: перемонтирование панели навигации теряет тап, который
  эту навигацию и вызвал.
- **Экран профиля** (`apps/miniapp/src/screens/ProfileScreen.tsx`): имя,
  `@username`, роль, Telegram ID, число оплаченных заказов и клубный статус с
  кнопкой перехода в канал. Открывается тапом по верхнему блоку. Выход — либо
  нативный `BackButton` (стек `View[]` в `App.tsx` уже синхронизирован с ним),
  либо любая вкладка нижней панели: выбор вкладки всегда сбрасывает стек, поэтому
  это работает без отдельной ветки на каждый экран.
- **Верхняя панель показывается только на основных экранах** (Каталог, Корзина,
  Заказы). На вложенных (товар, профиль) её нет: там есть `BackButton`, а
  полоса «нажмите, чтобы открыть профиль» внутри самого профиля была бы мёртвым
  элементом. Активная вкладка при этом остаётся подсвеченной — неподсвеченная
  панель читается как «вы нигде».
- **Механика клубного тарифа за подписку на канал.** Значение в БД — это
  клубный тариф `P` (цена для подписчика), стандартная цена выводится как
  `L = round(P / 0.95)`. Математика вынесена в `packages/shared/src/pricing.ts`
  (`standardUnitMinor`, `effectiveUnitMinor`, `tierAdjustmentMinor`,
  `cartTotals`) — один модуль на оба конца, чтобы приложение и API не могли
  посчитать по-разному. Целочисленная арифметика: `amount × 10000 / 9500` вместо
  `amount / 0.95`, иначе деньги уплывают на float. Округление **на единицу**, а
  не на строку: сервер хранит `unitAmountMinor` и умножает на количество, и
  округление итога строки расходилось бы с ним на минорную единицу.
- Утрата клубного тарифа стоит ~5.26%, а не 5%: `L = P / 0.95`, а не `P × 1.05`.
  Это закреплено тестом (`apps/api/src/pricing.test.ts`, 10 тестов), потому что
  перевёрнутое направление занижает выгоду подписки и внешне выглядит правдоподобно.
- **`Viewer.isSubscribedChannel`** в контракте (`packages/shared/src/telegram.ts`)
  и в ответе `GET /api/me`. Флаг приходит **только с сервера**, как и остальные
  факты о личности: клиент его не вычисляет и не присылает. Пока проверка
  `getChatMember` не подключена, сервер отдаёт `false` — значение уже имеет
  единственный источник, и включение реальной проверки меняет способ вычисления,
  а не место, откуда флаг берётся.
- **Плашки клубного тарифа** (`ClubTierNotice` в `components/ui.tsx`):
  на карточке товара над кнопкой действия — «Получите клубную выгоду 5%» со
  значком ℹ️ и предложением вступить в канал по тапу; в корзине — «Вы можете
  сохранить 5%» для неподписчиков и «Клубный тариф 5% активирован» для
  подписчиков. В корзине показаны оба состояния, на карточке — только
  приглашение: поздравление на каждой странице товара было бы шумом.
- Витрина каталога выводит цены штатно и одинаково для всех, без перечёркиваний:
  сетка зачёркнутых чисел читается как распродажа, а клубный тариф — постоянная
  ставка, а не акция.
- `VITE_CLUB_CHANNEL_URL` (`apps/miniapp/.env.example`) — публичная ссылка на
  канал. Пустое значение скрывает все точки перехода вместо открытия битой
  ссылки (`openChannel` в `telegram/webapp.ts`).

- **Главный экран Mini App стал персональным** (`apps/miniapp/src/screens/CatalogScreen.tsx`).
  Сверху — приветствие «Привет, {имя}» с инициалом вместо аватара, ниже заголовок
  «Каталог» и сетка категорий с иконкой и названием, затем прежняя витрина
  товаров. Тап по активной плитке снимает фильтр: иначе вернуться ко «всем
  товарам» можно было бы только прокруткой к нужной плитке.
- Профиль и категории запрашиваются **параллельно** через `useQueries`.
  Последовательные запросы удлинили бы загрузку на сумму обоих, а зависимости
  между ними нет: приветствию нужен `/api/me`, сетке — `/api/categories`.
  Неудача `/api/me` не ломает страницу: запрос идёт с `retry: false`, а
  приветствие становится нейтральным «Привет» — вне Telegram это гарантированный
  401, но каталог публичный и обязан работать.
- Скелетоны на время загрузки (`GreetingSkeleton`, `CategorySkeletonGrid` в
  `components/ui.tsx`) повторяют размеры контента, который замещают, — иначе
  шапка прыгает в момент прихода имени. Заголовок «Каталог» рисуется сразу:
  структура страницы не должна собираться на глазах у пользователя.
- Всё оформление — на CSS-переменных Telegram (`--tg-button-color`,
  `--tg-section-bg-color`, `--tg-hint-color`), поэтому светлая и тёмная темы
  клиента поддерживаются без отдельного кода. Пустой `emoji` у категории
  (так его пишет сид для «Карт AppStore») подменяется заглушкой `🗂`.

- **Появилось защищённое API управления магазином** (`apps/api/src/routes/admin.ts`).
  Каждый роут закрыт pre-handler'ом из `plugins/auth.ts`, а не проверкой внутри
  обработчика: pre-handler нельзя забыть на середине функции, и незащищённый
  роут виден при чтении списка роутов.

  | Роут | Право |
  | --- | --- |
  | `POST/PUT/DELETE /api/categories[/:id]` | `EDIT_CATALOG` |
  | `POST/PUT/DELETE /api/products[/:id]` | `MANAGE_KEYS` |
  | `GET /api/orders/all` | `VIEW_ORDERS` |
  | `GET/POST /api/managers`, `DELETE /api/managers/:telegramId` | `MANAGE_MANAGERS` |

- **`GET /api/orders/all`** отдаёт заказы всех покупателей вместе с данными
  клиента и `deliveredPayload` — это ровно то, что нужно для разбора статуса
  `FAILED`, и ровно то, что авторизует `VIEW_ORDERS`. Логика вынесена в
  отдельный `services/admin-orders.ts`: у `listOrdersForViewer` фильтр
  `where: { userId }` — единственное, что не даёт покупателю читать чужие
  заказы, и добавлять туда флаг «показать все» означало бы поставить инвариант
  в один неверный аргумент от отключения.
- **`POST /api/managers`** назначает менеджера по Telegram ID и задаёт полный
  набор прав (замена, а не слияние — интерфейс может присылать состояние
  чекбоксов целиком). Работает для пользователей, которые ещё не открывали
  приложение: строка создаётся заранее, имя перезапишется из Telegram при
  первом входе. Роль `ADMIN` через этот эндпоинт выдать нельзя, а попытка
  изменить права администратора из `ADMIN_TELEGRAM_IDS` отклоняется с
  `CONFLICT`: его доступ управляется окружением, и вторая точка выдачи полных
  прав создавала бы ложную картину.
- **`GET /api/managers`** показывает и менеджеров из БД, и администраторов из
  конфига — включая тех, у кого ещё нет строки в `User`, отдельной записью.
  Иначе список молча скрывал бы часть людей с полным доступом.
- Схемы управления собраны в `packages/shared/src/admin.ts`. Отдельно от
  `catalog.ts`, потому что публичное чтение никогда не отдаёт `staticPayload`,
  а запись обязана его принимать — эти формы не должны случайно оказаться одной
  схемой.
- Код ошибки `CONFLICT` (409) для нарушений уникальности: занятый `slug`
  возвращается клиенту понятным сообщением вместо `INTERNAL_ERROR`.
- **55 тестов управления** (`apps/api/src/routes/admin.test.ts`). 30 из них —
  таблица защиты: для каждого роута проверяется 401 без подписи, 403 для
  покупателя и 403 для менеджера с *другим* правом. Проверено мутацией: снятие
  одного guard'а роняет ровно 3 теста.


- **У пользователя появилась роль: `USER`, `MANAGER` или `ADMIN`.** Роль хранится
  строкой в `User.role` (по умолчанию `USER`) — как остальные «enum'ы» проекта,
  чтобы схема одинаково работала на SQLite и Postgres. Для `ADMIN` эта колонка —
  кеш решения по `ADMIN_TELEGRAM_IDS`, а не самостоятельный источник прав.
- **Права менеджеров хранятся отдельными строками в `ManagerPermission`.**
  Одно право = одна запись, уникальная в паре с `userId`. Массив или JSON-блоб
  в SQLite пришлось бы разбирать в приложении и нельзя было бы индексировать,
  а по строкам работает и выборка «кто имеет право X», и каскадное удаление
  вместе с пользователем.
- **Список прав — закрытый zod-enum `permissionSchema`** в
  `packages/shared/src/telegram.ts`: `EDIT_CATALOG`, `MANAGE_KEYS`,
  `VIEW_ORDERS`, `REFUND_ORDERS`, `MANAGE_MANAGERS`. Новое право добавляется
  сначала туда — иначе `requirePermission` его не примет.
- **Авторизация опирается на роль, а не на `isAdmin`.** После успешной проверки
  подписи initData `plugins/auth.ts` подтягивает `role` и список прав тем же
  запросом, что и upsert пользователя, поэтому `Viewer` содержит `role` и
  `permissions`. Поле `isAdmin` осталось в ответе как зеркало
  `role === 'ADMIN'` для совместимости, но ни одна проверка доступа его не читает.
- **Появились переиспользуемые проверки доступа для роутов.**
  `app.requireRole('ADMIN', 'MANAGER')` и `app.requirePermission('EDIT_CATALOG')`
  возвращают готовый pre-handler, который вешается на любой роут. В
  `requirePermission` роль `ADMIN` проходит без проверки конкретного права —
  иначе администратору пришлось бы выдавать все права поимённо, и добавление
  нового права ломало бы ему доступ.
- **15 тестов авторизации** (`apps/api/src/plugins/auth.test.ts`): роли, права,
  повышение и понижение по конфигу, отказ 401 против 403, невозможность выдать
  себе `ADMIN` через базу. Проверены мутациями — возврат старого поведения
  роняет тесты.
- Seed создаёт категории «ИИ», «Карты AppStore» и «Цифровые карты», а также
  заводит пользователей с ролью `ADMIN` по списку `ADMIN_TELEGRAM_IDS`.
  Идемпотентно: повторный запуск не перезаписывает имена, пришедшие из Telegram.

### Изменено

- **Профиль загружается один раз на всё приложение.** `CatalogScreen` больше не
  запрашивает `/api/me` сам: запрос переехал в хук `useViewer`
  (`apps/miniapp/src/api/useViewer.ts`) с тем же ключом `['me']`, и его читают
  шапка, карточка товара и корзина. Иначе клубный статус в шапке и в плашке над
  кнопкой мог бы разойтись — два независимых запроса возвращаются в разное время.
  `useQueries` в каталоге больше не нужен: осталась одна загрузка категорий.
- Приветствие `Greeting` и `GreetingSkeleton` удалены вместе с CSS-классами
  `.greeting*`: их роль перешла к `AppLayout` (`.app-header*`). Скелетон шапки
  по-прежнему совпадает по размеру с контентом, который замещает, — иначе шапка
  прыгает в момент прихода имени.
- Нижняя панель навигации переехала из `position: fixed` в нормальный поток
  (`.tab-bar`, `position: sticky` внутри флекс-колонки `.app-shell`): при
  `fixed` она перекрывала последнюю строку списка на коротких экранах. Отступ
  `.page` снизу теперь оставляет место только под нативную `MainButton`, которая
  плавает над WebView и в поток не входит.
- **Профиль вызывающего отдаёт один эндпоинт — `GET /api/me`.** Появившийся было
  `GET /api/users/me` возвращал то же самое под другим именем ключа (`user`
  против `viewer`), а так клиенты и начинают зависеть от того, который нашли
  первым. Остался `/api/me`: его уже вызывает Mini App. Сам обработчик переехал
  из `routes/orders.ts` в `routes/users.ts` — там ему место по смыслу.
- **Администраторы в сиде берутся из `ADMIN_TELEGRAM_IDS`.** Раньше в
  `apps/api/src/cli/seed.ts` лежала константа-плейсхолдер, которая сравнивалась
  сама с собой (`ADMIN_TELEGRAM_ID_PLACEHOLDER !== 'REPLACE_WITH_YOUR_...'`):
  условие всегда ложно, ветка недостижима, а чтобы её включить, нужно было
  править исходник и пересобирать. Теперь сид заводит по строке на каждый id из
  env — тот же источник, который проверяет `plugins/auth.ts`, поэтому
  разъехаться они не могут.
- Вход администратора больше не делает два запроса к БД. Роль вычисляется до
  `upsert` и пишется вместе с остальными полями; отдельный `UPDATE` выполняется
  только когда сохранённая роль действительно расходится с вычисленной.
- В `plugins/auth.ts` возвращены комментарии, объясняющие неочевидное: почему
  плагин обёрнут в `fastify-plugin`, почему клиент не сообщает свой `user_id`,
  зачем нужен fallback-заголовок и почему dev-обход безопасен только вне
  production. Форматирование приведено к ширине, принятой в остальном коде.
- **Обслуживающие скрипты запускаются на сервере без `tsx`.** Сид базы и
  регистрация вебхука были `.ts`-файлами (`apps/api/prisma/seed.ts`,
  `apps/api/scripts/webhook.ts`) и ехали в артефакт как исходники, а `tsx`,
  которым они выполнялись, — devDependency. После перехода на production-only
  `node_modules` в артефакте `npm run db:seed` и `npm run bot:set-webhook` на
  сервере просто перестали существовать. Теперь оба скрипта живут в
  `apps/api/src/cli/`, компилируются обычным `tsc` вместе с API и запускаются
  в продакшене как `node --env-file=/srv/shop/shared/api.env dist/cli/seed.js`
  и `… dist/cli/webhook.js set`. В разработке команды не изменились.
  `pack-artifact.mjs` больше не кладёт в архив `.ts`-файлы, зато требует
  наличия `dist/cli/seed.js` и `dist/cli/webhook.js`: импортов на них нет,
  поэтому выпадение из сборки иначе всплыло бы только на сервере.
  **BREAKING:** на сервере `npm run db:seed`/`npm run bot:set-webhook` больше
  не работают — используйте команды выше (`docs/DEPLOYMENT.md`, раздел 4).
- **Сервер больше не устанавливает зависимости: `node_modules` едут в
  артефакте.** `npm ci --omit=dev` на VPS убивал OOM killer
  (`Killed  npm ci --omit=dev`) — production-граф это ~13 800 файлов и ~370 МБ,
  памяти машины не хватает даже без devDependencies. Виновник размера —
  необязательные peer-зависимости `@prisma/client` (`prisma` и `typescript`):
  npm ставит их по умолчанию, а в `package-lock.json` у них нет флага `dev`,
  поэтому `--omit=dev` их не отсекает. Теперь дерево целиком собирает runner
  (`npm ci --omit=dev` со включёнными install-скриптами, чтобы `better-sqlite3`
  получил нативный бинарник) и кладёт в архив. `deploy.sh` распаковывает,
  применяет схему и переключает симлинк — npm на сервере не запускается вообще.
- **Проверка совместимости артефакта стала фатальной.** Вместе с зависимостями
  уезжает нативный `better-sqlite3`, годный ровно для одной пары ОС/архитектура
  и одного ABI Node. `artifact.json` теперь содержит `platform`, `arch` и
  `bundledDependencies`, а `deploy.sh` при расхождении с хостом **отказывается
  ставить релиз** вместо прежнего предупреждения: иначе несовместимость всплыла
  бы загадочной ошибкой загрузки модуля на первом запросе к базе. Артефакты без
  `bundledDependencies` (старые) обрабатываются по-прежнему.
- Размер артефакта вырос с ~0,2 МБ до ~100 МБ в gzip. Осознанный обмен: scp
  занимает секунды, а установка зависимостей на этой машине невозможна.
- `deploy.sh` больше не глушит вывод `prisma db push` через `tail -5` —
  диагностическая часть ошибки Prisma доходила до логов обрезанной.
- `deploy/pack-artifact.mjs` заменяет workspace-симлинки `node_modules/@shop/*`
  реальными собранными пакетами: npm создаёт их указывающими на чекаут runner'а,
  и на сервере такие ссылки висели бы в пустоту. Внутри `node_modules` файлы
  `.d.ts` и `.map` больше не вырезаются — часть пакетов обращается к ним
  в рантайме.

### Исправлено

- **Частичный `PUT` больше не затирает поля, которых не было в запросе.**
  Схемы обновления сначала были сделаны как `.partial()` от схем создания, но
  `.partial()` не снимает `.default()`: `PUT { sortOrder: 5 }` разбирался в
  `{ sortOrder: 5, description: '', currency: 'XTR', isActive: true }` — то есть
  стирал описание товара и **заново включал скрытый товар в продажу**. Поймано
  проверкой разбора схемы до написания роутов, а не в рантайме. Схемы
  `*UpdateSchema` теперь объявляют поля без дефолтов, а сервис пишет только
  ключи, реально присутствующие во входных данных (`undefined` — «не трогать»,
  `null` — «очистить колонку»).
- `DELETE /api/products/:id` деактивирует товар, а не удаляет: `OrderLine`
  ссылается на товар с `onDelete: Restrict`, поэтому заказанный товар удалить
  нельзя физически — и не нужно, иначе старые заказы перестанут читаться.
  `DELETE /api/categories/:id` удаляет категорию, но её товары остаются и лишь
  теряют группировку (`onDelete: SetNull`).
- Заливка ключей идемпотентна: дубликаты внутри запроса и уже существующие
  ключи отфильтровываются до вставки. `createMany({ skipDuplicates })` для
  этого не подошёл — SQLite-коннектор Prisma его не поддерживает (тип `never`),
  и один повторяющийся ключ ронял бы весь батч на уникальном индексе
  `(productId, secret)`.
- **Деплой вставал насмерть, когда `releases/` забивал диск.** С переходом на
  самодостаточные артефакты каждый релиз несёт свои production `node_modules`
  (~400 МБ распакованными), а `KEEP_RELEASES` оставался равным 5 — как в те
  времена, когда релиз был парой мегабайт кода. Пять релизов заняли диск VPS
  (9.7 ГБ) под 100%, и очередной деплой умер внутри `tar` с `No space left on
  device`. Хуже всего то, что чистка старых релизов стояла **последним** шагом
  скрипта: до кода, который освободил бы место, выполнение не доходило никогда,
  и стенд требовал ручного входа по SSH. Теперь `KEEP_RELEASES=2` (активный плюс
  одна цель откату), а чистка выполняется **дважды**: до распаковки
  (`KEEP_RELEASES - 1`, последний слот занимает новый релиз) и после
  переключения симлинка. Деплой, упавший из-за места, чинится следующим
  запуском сам. Активный релиз не является кандидатом на удаление ни на одном
  из проходов, поэтому возможность откатиться сохраняется всё время деплоя.
- **Нехватка места сообщается до распаковки, а не из середины `tar`.**
  `deploy.sh` сверяет свободное место с пятикратным размером архива
  (`node_modules` сжимается примерно вчетверо, остальное — запас на
  `prisma db push` и базу) и при недостатке печатает размеры релизов, команды
  расчистки и завершается, ничего не изменив. Ошибка `tar` тоже перестала быть
  загадочной: в сообщении теперь упоминается диск.
- Логика чистки вынесена в функцию `prune_releases()` вместо копии кода в конце
  скрипта. Побочно исправлено: при висящем симлинке `current` (например, если
  активный релиз удалили руками, чтобы освободить место) резервировался слот под
  несуществующий каталог, и на диске оставалось на один релиз меньше, чем
  обещает `KEEP_RELEASES`.
- После успешного деплоя печатается занятость диска — чтобы приближение к
  границе было видно в логах CI заранее, а не по упавшему деплою.
- **Использованный артефакт удаляется из `incoming/`.** Ещё ~100 МБ мёртвым
  весом на самом дефицитном ресурсе стенда: после распаковки архив никто не
  читает, а CI загружает свежую копию при каждом запуске. Удаляется строго тот
  файл, который скрипт только что установил, вместе с его `.sha256`, и только
  если он лежит в `incoming/`: артефакт, переданный аргументом из другого
  каталога, принадлежит вызывающему и не трогается. **Следствие:** повторный
  запуск `deploy.sh` (включая `FORCE=1`) после удачного деплоя архива уже не
  найдёт — нужно перезапустить workflow. Для отката архив не нужен: это
  переключение симлинка на уже распакованный релиз.

- **Удачный деплой мог отрапортовать неудачу.** Чистка старых релизов в
  `deploy.sh` выполняется уже **после** переключения симлинка, но её конвейер
  (`ls -1dt */ | tail -n +N | while read`) при `set -euo pipefail` мог вернуть
  ненулевой код: `ls` падает, если glob ничего не нашёл, а `tail` — на SIGPIPE.
  В результате сайт работал и отвечал 200, а шаг деплоя горел красным и
  `Deployed ... successfully` не печаталось. Теперь список релизов собирается
  отдельно с `|| true`, а неудачное удаление каталога печатает предупреждение
  вместо срыва скрипта.

- **Убран несуществующий параметр `script_stop` у `appleboy/ssh-action@v1`.**
  Actions логировал `Unexpected input(s) 'script_stop'` и игнорировал его:
  в `action.yml` такого входа нет, а `entrypoint.sh` не пробрасывает
  `INPUT_SCRIPT_STOP` в `drone-ssh`. Поведение «падать на первой ошибке»
  обеспечивает `set -euo pipefail` в первой строке самого скрипта, так что
  фактическая логика деплоя не меняется — уходит только шум в логах.

- **CI падал на любом чистом чекауте.** `packages/shared/dist` лежит в
  `.gitignore`, а `@shop/shared` резолвится через `"types": "./dist/index.d.ts"`,
  но в workflow сборка стояла **после** typecheck и тестов. В результате
  контракт не был собран к моменту проверки: 9 ошибок `TS2307` («Cannot find
  module `@shop/shared`») и каскадные `TS7006` implicit any у `line` в
  `apps/api/src/routes/bot.ts`, `i` в `telegram/init-data.ts` и `line` в
  `apps/miniapp/src/screens/OrdersScreen.tsx`. Тесты падали там же с
  `ERR_MODULE_NOT_FOUND`. Теперь `packages/shared` собирается скриптом
  `prepare` при `npm ci`, то есть до первой проверки; локальный клон тоже
  больше не требует ручного `npm run build`. Типы `line` и `i` специально
  оставлены выводимыми: они корректно приходят из Prisma, а ручная аннотация
  разошлась бы со схемой при первом же её изменении.
- Скрипт `prepare` тихо выходит, если `tsc` недоступен. Без этой проверки
  `npm ci --omit=dev` в `deploy/deploy.sh` падал бы на сервере: в артефакте нет
  ни `src`, ни `tsconfig.json`, ни TypeScript, а `prepare` выполняется даже с
  `--omit=dev`.
- Шаг «Verify the shared contract was built» в workflow проверяет наличие
  `dist/index.d.ts` сразу после установки: если контракт снова перестанет
  собираться, CI упадёт с понятным сообщением, а не с 12 запутанными
  ошибками типов.
- **`git submodule` возвращал код 128.** Каталог
  `opencode-agentrouter-support/` был закоммичен как gitlink (mode `160000`)
  без записи в `.gitmodules`, поэтому `git submodule status` и
  `git submodule foreach` завершались с `fatal: no submodule mapping found`.
  Коммит, на который указывал gitlink, недоступен ни в одном remote, так что
  свежий клон получал пустой каталог. Каталог убран из индекса
  (`git rm --cached`, файлы на диске не тронуты) и добавлен в `.gitignore`.

### Изменено

- **Сборка перенесена с VPS в GitHub Actions.** Раньше сервер делал `npm ci`
  со всеми devDependencies (~425 МБ) и запускал `tsc` + `vite build` — на слабой
  машине это минуты полной загрузки CPU и риск, что OOM killer прибьёт
  работающий процесс. Теперь runner собирает проект и передаёт архив ~0.2 МБ,
  а сервер только распаковывает его, ставит production-зависимости
  (`npm ci --omit=dev`, ~100 МБ) и переключает симлинк.
- `deploy/deploy.sh` больше не собирает код: принимает путь к артефакту,
  проверяет sha256 и мажор Node из `artifact.json`, распаковывает, ставит
  зависимости, применяет схему и переключает релиз. Атомарное переключение,
  health-check и автоматический откат сохранены. Незавершённый релиз удаляется
  по `trap`, чтобы битый каталог не приняли за цель отката.
- `.github/workflows/deploy.yml` разделён на job `build` (typecheck, тесты,
  сборка, упаковка, публикация артефакта на 14 дней) и `deploy` (scp архива,
  синхронизация deploy-скриптов на нужный коммит, установка, проверка
  публичного `/health`). Артефакт загружается до запуска установки: обрыв
  передачи не должен перезапускать сервис.
- `deploy/setup-server.sh` создаёт каталог `incoming/` для артефактов и
  обновляет клон репозитория при повторном запуске. Из репозитория на сервере
  теперь нужны только deploy-скрипты и конфиги — код приезжает артефактом.
- `README.md` — раздел про деплой заменён ссылкой на `docs/DEPLOYMENT.md`,
  добавлена навигация по документации.

### Добавлено

- `deploy/pack-artifact.mjs` и команда `npm run pack` — упаковка
  развёртываемого артефакта: скомпилированный код, манифесты воркспейсов,
  `package-lock.json`, схема и конфиг Prisma, `artifact.json` с коммитом и
  версией Node. Без `node_modules`, исходников, `.map` и `.d.ts`. Рядом
  пишется файл `.sha256` для проверки целостности при доставке.
- `AGENTS.md` — точка входа для ИИ-ассистентов: протокол входа в проект,
  инварианты безопасности, правила работы с кодом, границы допустимого.
- `docs/ARCHITECTURE.md` — карта кода: структура каталогов, поток покупки,
  модель данных, список эндпоинтов, таблица «задача → файлы», обоснования
  принятых решений.
- `docs/DEPLOYMENT.md` — деплой и эксплуатация продакшена: раскладка на VPS,
  первичная настройка, откат, бэкап, таблица диагностики деплоя.
- `CHANGELOG.md` — этот файл.

### Исправлено

- Проверка драйвера SQLite в CI и при деплое обращалась к `better-sqlite3`
  напрямую, хотя приложение его не импортирует: Prisma-адаптер использует
  собственную вложенную копию другой версии. Проверка могла пройти при
  нерабочем драйвере и наоборот. Теперь проба идёт через
  `@prisma/adapter-better-sqlite3` — то, что реально загружается в рантайме.

  не превращается в непонятную ошибку на середине деплоя.

## [0.1.0] — 2026-08-23

Первая рабочая версия: магазин цифровых товаров в Telegram Mini App с оплатой
Telegram Stars и автоматической выдачей ключей в чат.

### Добавлено

- **Контракт `packages/shared`** — zod-схемы и типы, общие для фронта и бэка:
  деньги в минорных единицах (`money.ts`), каталог (`catalog.ts`), заказы
  (`order.ts`), `initData` и `Viewer` (`telegram.ts`), коды ошибок с
  автоматическим маппингом на HTTP-статусы (`errors.ts`).
- **API `apps/api`** на Fastify 5: публичный каталог, заказы, `/api/me`,
  `/health`, вебхук Telegram. Rate limit 300 req/min, для создания заказа —
  20 req/min. Единый формат ошибки `{ error: { code, message, details? } }`.
- **Проверка `initData`** по алгоритму Telegram: HMAC-SHA256,
  constant-time сравнение, контроль срока жизни, поле `signature` включено
  в строку проверки.
- **Схема БД** (Prisma 7 + SQLite через driver adapter): `User`, `Category`,
  `Product`, `LicenseKey`, `Order`, `OrderLine`, `ProcessedUpdate`.
  Postgres-совместима, enum'ы хранятся строками.
- **Логика заказов** `services/orders.ts`: цены и остатки из БД, запрет
  смешивания валют в одном заказе, выдача ключей условным `UPDATE`,
  идемпотентный `markOrderPaid`, мгновенная выдача бесплатных заказов.
- **Бот на grammY**: команды `/start` и `/orders`, обработка
  `pre_checkout_query`, выдача товара по `successful_payment`, обработка
  `refunded_payment`. Дедупликация апдейтов по `update_id`.
- **Платёжный слой** `payments/gateway.ts`: Telegram Stars (XTR) или внешний
  провайдер, переключается через `PAYMENT_PROVIDER`. Логика заказов от
  провайдера не зависит.
- **Mini App `apps/miniapp`** на React 19 + Vite: каталог с фильтром по
  категориям, карточка товара, корзина, список заказов с выдачей ключей.
  Нативные `MainButton`/`BackButton`, haptics, тема Telegram через
  CSS-переменные, работа в обычном браузере с dev-авторизацией.
- **Корзина** на Zustand с persist в localStorage; цена хранится только для
  отображения.
- **Тесты**: 32 теста на `node:test` — 14 на проверку подписи `initData`,
  18 e2e через `app.inject()` на временной SQLite-базе.
- **Демо-каталог** `prisma/seed.ts`: 3 категории, 5 товаров всех типов выдачи
  (ключ, файл, ссылка, бесплатный), идемпотентный.
- **Деплой на VPS** `deploy/`: Caddy с автосертификатом и CSP под Telegram,
  ужатый systemd-юнит, идемпотентный `setup-server.sh`, `deploy.sh` с
  атомарным переключением релиза и автоматическим откатом по `/health`.
- **CI** `.github/workflows/deploy.yml`: typecheck → тесты → сборка, и только
  затем деплой по SSH с проверкой публичного `/health`.

### Безопасность

- Личность пользователя определяется только по подписи Telegram; клиент не
  может сообщить свой `user_id`.
- Цены и суммы вычисляются на сервере из БД; `amountMinor`, `totalAmountMinor`
  и `status` из тела запроса игнорируются.
- `deliveredPayload` заполняется только после подтверждённой оплаты.
- Склад — строки `LicenseKey`, а не счётчик: одновременные покупатели не могут
  получить один ключ.
- Повторная обработка платежа не выдаёт второй ключ.
- Чужой заказ отдаёт 404, а не 403 — существование заказов не раскрывается.
- `staticPayload` (оплачиваемый контент) никогда не попадает в API-ответ.
- В логах маскируются `authorization`, `x-telegram-init-data`,
  `x-telegram-bot-api-secret-token`.
- Production не запускается без токена бота, без секрета вебхука или с
  `ALLOW_DEV_AUTH=true`.
- `VITE_DEV_TELEGRAM_ID` вырезается из production-бандла на этапе сборки.
- На сервере: порт API закрыт извне, HSTS, CSP с `frame-ancestors` для
  Telegram, деплой-пользователь может перезапускать только свой сервис.

### Известные ограничения

- Админки нет: товары и ключи заливаются через seed или Prisma Studio.
- Загрузка изображений не реализована, `imageUrl` заполняется вручную.
- Возврат Stars нельзя инициировать из интерфейса.
- Заказы в статусе `FAILED` (оплачен, но не выдан) не мониторятся.
- Миграции Prisma не ведутся, используется `db push`.
