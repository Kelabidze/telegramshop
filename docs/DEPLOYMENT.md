# Деплой и эксплуатация

Продакшен-стенд: `ochkisk.shop` → `176.119.156.77`, один VPS под Ubuntu.
Caddy отдаёт статику Mini App и проксирует `/api`, `/health`, `/telegram/*`
на Node-процесс под systemd. База — файл SQLite на диске.

**Сборка идёт на GitHub Actions, не на VPS.** Сервер получает готовый архив
~100 МБ — со скомпилированным кодом **и установленными зависимостями** — и
только распаковывает его и переключает симлинк. Ни `tsc`, ни `vite`, ни
`npm ci` на слабой машине не запускаются.

---

## 1. Раскладка на сервере

```
/srv/shop/
├── repo/                  git-клон: ТОЛЬКО deploy-скрипты и конфиги сервера
├── incoming/              сюда CI загружает artifact.tar.gz; пустеет после установки
├── releases/              распакованные релизы с таймстемпом (хранится 2)
├── caddy/                 staging для конфига Caddy (см. раздел 6)
├── current -> releases/…  симлинк на активный релиз
└── shared/
    ├── api.env            секреты; деплой их не трогает
    └── data/prod.db       база; переживает деплои
```

Логика: артефакт распаковывается в **новый** каталог, и только после успешного
health-check симлинк `current` остаётся переключённым. Сломанный релиз не может
уронить работающий сайт.

**Релизов хранится два, и это не запас на будущее, а предел диска.** Каждый
релиз несёт собственные production `node_modules` — около 400 МБ в распакованном
виде. При `KEEP_RELEASES=5` каталог `releases/` занимал больше 2 ГБ, и на диске
9.7 ГБ это привело к 100% занятости: следующий деплой умер внутри `tar` с
`No space left on device`. Два релиза — это активный плюс одна цель откату,
больше на этой машине не помещается. Значение переопределяется переменной
`KEEP_RELEASES`.

## 2. Почему сборка в CI

Раньше VPS делал `npm ci` со всеми devDependencies (~425 МБ: TypeScript, Vite,
Prisma CLI, тестовый тулинг), затем `tsc` и `vite build`. На слабой машине это
2–4 минуты полной загрузки CPU и реальный риск, что OOM killer прибьёт
работающий процесс прямо во время деплоя.

Сборку вынесли в CI, но `npm ci --omit=dev` на сервере остался — и всё равно
падал: `Killed  npm ci --omit=dev`. Даже production-граф (~13 800 файлов,
~370 МБ) не влезает в память этой машины. Поэтому зависимости тоже уехали в
артефакт, и сервер больше не запускает npm вообще.

Теперь тяжёлую часть делает бесплатный 4-ядерный runner GitHub, а на сервер
уезжает всё, что нужно для запуска:

| Этап | Раньше на VPS | Сейчас на VPS |
| --- | --- | --- |
| `npm ci` | ~425 МБ, с devDeps | нет, зависимости готовые в архиве |
| `tsc` + `vite build` | 2–4 мин CPU | нет |
| Передача | `git fetch` | архив ~100 МБ |
| Итого | минуты, риск OOM | десятки секунд, без OOM |

**Что в артефакте** (`npm run pack` → `deploy/pack-artifact.mjs`):
скомпилированные `apps/api/dist`, `apps/miniapp/dist`, `packages/shared/dist`,
манифесты всех workspace-пакетов, `package-lock.json`, схема и конфиг Prisma,
**готовые production `node_modules`**, `artifact.json` с коммитом, версией Node
и платформой сборки. Без `.map`, `.d.ts` и исходников (внутри `node_modules`
они сохраняются — некоторые пакеты грузят их в рантайме).

**Обслуживающие скрипты — тоже часть `dist`.** Сид базы и регистрация вебхука
живут в `apps/api/src/cli/` и компилируются вместе с API в `dist/cli/seed.js`
и `dist/cli/webhook.js`. Раньше это были `prisma/seed.ts` и `scripts/webhook.ts`,
которые ехали в артефакт как `.ts` и запускались через `tsx` — а `tsx` лежит в
devDependencies, которых на сервере нет. `pack-artifact.mjs` проверяет наличие
обоих файлов в списке `REQUIRED_BUILD_OUTPUTS`: на них никто не ссылается
импортом, поэтому выпадение из сборки заметно только на сервере.

**Почему `node_modules` внутри.** Сервер не выполняет ни `npm ci`, ни
`npm install`. Раньше выполнял — и падал: разрешение графа зависимостей
(~13 800 файлов, ~370 МБ на диске) не влезает в память VPS, процесс убивал
OOM killer прямо посреди деплоя. Поэтому дерево зависимостей целиком собирает
runner (`npm ci --omit=dev` со включёнными install-скриптами, чтобы
`better-sqlite3` получил свой нативный бинарник) и кладёт в архив.

**Цена решения.** `better-sqlite3` — нативный модуль, скомпилированный под
конкретную ОС, архитектуру и ABI Node. Значит артефакт годен **только** для той
платформы, где собран. `artifact.json` хранит `nodeMajor`, `platform` и `arch`,
а `deploy.sh` при расхождении **отказывается устанавливать релиз** — иначе
несовместимость всплыла бы загадочной ошибкой загрузки модуля на первом
запросе к базе. Отсюда требование: **мажорная версия Node в CI и на сервере
должна совпадать.** В workflow она задана в `env.NODE_VERSION`, на сервере её
ставит `setup-server.sh` (`NODE_MAJOR`); сейчас и там и там 22.

Размер архива из-за этого вырос с ~0,2 МБ до ~100 МБ. Это осознанный обмен:
передача по scp занимает секунды, а установка зависимостей на сервере
невозможна в принципе.

## 3. Первичная настройка сервера (один раз)

На VPS под root:

```bash
curl -fsSL https://raw.githubusercontent.com/Kelabidze/telegramshop/main/deploy/setup-server.sh | sudo bash
```

Скрипт идемпотентный, повторный запуск безопасен. Что делает:

- ставит Node 22, Caddy, build-essential (страховка, если для какой-то
  платформы не окажется готового бинарника SQLite);
- создаёт пользователя `shop` с `/bin/bash` и заблокированным паролем
  (вход только по SSH-ключу — иначе деплой из GitHub Actions не сработает);
- создаёт раскладку каталогов, включая `incoming/` для артефактов и `caddy/`
  для staging конфига реверс-прокси;
- клонирует репозиторий **от имени `shop`** — на сервере из него нужны только
  `deploy/*` и конфиги, код приезжает артефактом;
- генерирует `TELEGRAM_WEBHOOK_SECRET` и создаёт `shared/api.env`; на уже
  настроенном сервере добавляет только отсутствующий `NODE_ENV=production`, не
  перезаписывая секреты или другие локальные настройки;
- ставит Caddyfile (через тот же `sync-caddy.sh`, что работает при деплое) и
  systemd-юнит, подставляя домен;
- выдаёт `shop` право на `systemctl restart|status|is-active shop-api` и на
  четыре команды для синхронизации Caddy — полный список в разделе 6;
- включает ufw: наружу только 22/80/443, порт 8080 закрыт;
- проверяет, что DNS домена указывает на этот сервер.

Переопределение по умолчанию: `DOMAIN=... REPO_URL=... sudo bash deploy/setup-server.sh`.

Затем впишите токен бота:

```bash
sudo nano /srv/shop/shared/api.env      # TELEGRAM_BOT_TOKEN=...
```

Остальное уже заполнено, включая `PUBLIC_API_URL=https://ochkisk.shop`.
В production сервер **не стартует** без токена, без секрета вебхука или с
`ALLOW_DEV_AUTH=true` — это защита, а не придирка.

## 4. Деплой

**Автоматически:** push в `main` → `.github/workflows/deploy.yml`.

Job `build` на runner'е: `npm ci` → проверка сборки контракта → проверка
драйвера SQLite → `prisma generate` → typecheck → тесты → `npm run build` →
установка production-зависимостей в `build/prod-deps` → `npm run pack`.
Артефакт публикуется в Actions (хранится 14 дней) — полезно, чтобы посмотреть,
что именно уехало.

Job `deploy`: скачивает артефакт, копирует по scp в `/srv/shop/incoming/`,
подтягивает deploy-скрипты на нужный коммит и запускает `deploy.sh`. В конце
проверяет публичный `/health`.

Порядок важен: сначала загрузка файла, только потом установка. Оборвавшаяся
передача не должна перезапускать сервис.

**Вручную на сервере** (артефакт уже в `incoming/`):

```bash
sudo -u shop bash /srv/shop/repo/deploy/deploy.sh /srv/shop/incoming/artifact.tar.gz
```

Успешный деплой **удаляет использованный архив** из `incoming/` — это ~100 МБ,
которые больше никто не читает, а CI загружает свежую копию при каждом запуске.
Поэтому ре-деплой того же коммита (`FORCE=1 bash …/deploy.sh`) сработает только
если архив на месте: скачайте его заново из артефактов workflow или просто
перезапустите workflow. Откатиться на предыдущий релиз архив не нужен вообще —
это переключение симлинка, см. раздел 5.

Удаляется строго тот файл, который скрипт только что установил, и только если он
лежит в `incoming/`. Артефакт, переданный аргументом из другого каталога, не
трогается: он принадлежит тому, кто его туда положил.

**Собрать артефакт локально** (например, если GitHub недоступен):

**Собрать артефакт локально важно с оговоркой:** нативный `better-sqlite3`
собирается под текущую платформу, поэтому артефакт, собранный на Windows или
macOS, `deploy.sh` на сервере отвергнет. Локальная сборка годится для Linux
x64 с тем же мажором Node, что на сервере.

```bash
npm run build
# то же, что делает CI перед упаковкой:
mkdir -p build/prod-deps && cp package.json package-lock.json build/prod-deps/
for p in packages/shared apps/api apps/miniapp; do
  mkdir -p "build/prod-deps/$p" && cp "$p/package.json" "build/prod-deps/$p/"
done
npm ci --omit=dev --prefix build/prod-deps
npm run pack                                    # build/artifact.tar.gz
scp build/artifact.tar.gz* shop@176.119.156.77:/srv/shop/incoming/
ssh shop@176.119.156.77 'bash /srv/shop/repo/deploy/deploy.sh'
```

Что делает `deploy.sh`:

1. проверяет sha256 архива и что это валидный tar.gz;
2. читает `artifact.json`; при `bundledDependencies: true` **отказывается
   ставить релиз**, если мажор Node, ОС или архитектура не совпадают с хостом;
   пропускает работу, если этот коммит уже live;
3. **освобождает место до распаковки**: удаляет старые релизы, оставляя
   `KEEP_RELEASES - 1` (активный никогда не кандидат), затем сверяет свободное
   место с пятикратным размером архива и отказывается начинать, если не влезет;
4. распаковывает в новый каталог релиза;
5. проверяет, что зависимости на месте и нативный драйвер SQLite загружается
   (установки нет — дерево пришло готовым);
6. `prisma db push` — только добавляет недостающие таблицы и колонки;
7. **синхронизирует `/etc/caddy/Caddyfile`** с `deploy/Caddyfile` из
   разворачиваемого коммита (раздел 6); при неудаче деплой останавливается
   **до** переключения симлинка, и продолжает работать текущий релиз;
8. атомарно переключает `current` и перезапускает сервис;
9. ждёт `/health` до 20 секунд и **при неудаче откатывается** на предыдущий
   релиз (неудачный остаётся на диске — по нему разбирают причину), а вместе с
   кодом возвращает и предыдущий Caddyfile;
10. дочищает то, что вытеснил новый релиз, оставляя `KEEP_RELEASES` (по
    умолчанию 2) и никогда не удаляя активный;
11. удаляет использованный архив из `incoming/` и печатает занятость диска.

Незавершённый релиз удаляется по `trap`, чтобы битый каталог потом не приняли
за цель отката — и чтобы неудачная распаковка не держала на диске сотни
мегабайт.

**Почему чистка идёт до распаковки, а не только после.** Раньше prune стоял
единственным шагом в конце. Когда `releases/` забил диск, деплой падал внутри
`tar` — то есть до кода, который освободил бы место, дело не доходило, и
единственным выходом был ручной вход по SSH. Теперь неудачный из-за диска деплой
чинится следующим запуском сам. Шаг чистки выполняется **до** переключения
симлинка, поэтому удаляется только старая цель откату, а активный релиз и
возможность вернуться на него сохраняются на всём протяжении деплоя.

## 4. Вебхук и BotFather

```bash
cd /srv/shop/current/apps/api
sudo -u shop node --env-file=/srv/shop/shared/api.env dist/cli/webhook.js set
```

Регистрирует `https://<домен>/telegram/webhook` с secret token и подпиской
на `message`, `pre_checkout_query`, `callback_query` (последний пока не
обрабатывается, подписка на него — задел на будущее). Снять вебхук —
`dist/cli/webhook.js delete`. Затем в @BotFather: `/newapp` → Web App URL =
`https://ochkisk.shop`.

Наполнить каталог демо-товарами:

```bash
cd /srv/shop/current/apps/api
sudo -u shop node --env-file=/srv/shop/shared/api.env dist/cli/seed.js
```

**Почему `node`, а не `npm run`.** В артефакте нет devDependencies, а значит нет
и `tsx`, которым эти скрипты запускаются в разработке. Поэтому они лежат в
`apps/api/src/cli/` и компилируются обычным `tsc` вместе с остальным API — на
сервер приезжают готовые `dist/cli/seed.js` и `dist/cli/webhook.js`. `npm run
db:seed` и `npm run bot:set-webhook` на сервере работать не будут: это dev-скрипты.

`--env-file` обязателен: systemd читает `api.env` сам, а запущенный руками
процесс — нет, и без токена бота `config.ts` откажется стартовать.

## 5. Эксплуатация

```bash
sudo systemctl status shop-api          # состояние
sudo journalctl -u shop-api -f          # логи в реальном времени
sudo systemctl restart shop-api         # перезапуск
curl -s localhost:8080/health           # health изнутри сервера
sudo journalctl -u caddy -n 30          # проблемы с сертификатом
```

Откат вручную:

```bash
ls -1t /srv/shop/releases                                    # выбрать нужный
sudo -u shop ln -sfnT /srv/shop/releases/<релиз> /srv/shop/current.new
sudo -u shop mv -Tf /srv/shop/current.new /srv/shop/current
sudo systemctl restart shop-api
```

Бэкап базы (SQLite — один файл):

```bash
sudo -u shop cp /srv/shop/shared/data/prod.db \
                /srv/shop/shared/data/backup-$(date +%F).db
```

### Загруженные медиафайлы

Баннеры и картинки товаров лежат в `/srv/shop/shared/uploads` и раздаются Caddy
как `/uploads/*`. Каталог **вне** релиза сознательно: деплой удаляет старые
релизы, и всё внутри них исчезло бы. `UPLOADS_DIR` в `api.env` указывает туда же.

В базе хранится только путь, поэтому бэкап `prod.db` без этого каталога
восстановит витрину с битыми картинками:

```bash
sudo -u shop tar -czf /srv/shop/shared/uploads-$(date +%F).tar.gz \
  -C /srv/shop/shared uploads
du -sh /srv/shop/shared/uploads     # квота 200 МБ, проверяется при загрузке
```

Права `755`, в отличие от `data/` (`750`): Caddy работает под своим
пользователем и должен читать эти файлы. База остаётся закрытой.

### Место на диске

Самый вероятный способ уронить деплой на этом стенде. Диск 9.7 ГБ, каждый релиз
занимает ~400 МБ, поэтому за занятостью стоит поглядывать:

```bash
df -h /                                 # общая картина
du -sh /srv/shop/releases/*/            # сколько занимает каждый релиз
readlink -f /srv/shop/current           # какой релиз активен (его не удалять!)
ls -1t /srv/shop/releases               # новейшие сверху
```

В норме занятость стабильна: релизов не больше двух, а `incoming/` очищается
после каждой успешной установки. Расти диску есть с чего только по трём
причинам — бэкапы базы (делаются вручную, никто их не удаляет), логи systemd и
кеш apt.

Ручная расчистка, если места уже нет и деплой не проходит. Сначала узнайте
активный релиз, потом удаляйте остальные **по одному, по имени** — так нельзя
случайно снести работающий сайт:

```bash
readlink -f /srv/shop/current                       # активный релиз
ls -1t /srv/shop/releases                           # остальные — кандидаты
sudo -u shop rm -rf /srv/shop/releases/<релиз>      # повторить для ненужных
```

Что ещё можно освободить безопасно:

```bash
sudo rm -f /srv/shop/incoming/artifact.tar.gz*      # CI загрузит заново
sudo apt-get clean                                  # кеш пакетов
sudo journalctl --vacuum-size=100M                  # старые логи systemd
ls -la /srv/shop/shared/data/                       # старые backup-*.db
```

`incoming/` чистить безопасно: артефакт заново загружает CI при каждом деплое.
Активный релиз удалять нельзя — сервис читает файлы оттуда прямо сейчас, как и
`shared/data/prod.db`. После расчистки достаточно перезапустить workflow: обычный
деплой сам приведёт `releases/` к двум каталогам.

## 6. Конфиг Caddy: источник истины и синхронизация

**`deploy/Caddyfile` в Git — источник истины.** Каждый деплой приводит
`/etc/caddy/Caddyfile` в соответствие с ним. Правка, сделанная прямо на сервере,
переживёт ровно до следующего деплоя, который затронет конфиг.

Так было не всегда, и это стоило продакшену видимой поломки. Конфиг ставил
только `setup-server.sh`, а он выполняется один раз при первичной настройке.
Блок `handle /uploads/*` лежал закоммиченным, но не установленным пять деплоев
подряд: картинки баннеров отдавались как `index.html` со статусом 200, и витрина
показывала пустые кадры. Git и сервер разошлись молча — именно потому, что
ничто их не сверяло.

### Как работает `deploy/sync-caddy.sh`

Одна реализация на два вызова: `setup-server.sh` запускает её от root при
первичной настройке, `deploy.sh` — от непривилегированного `shop` при каждом
деплое. Две копии этой последовательности разъехались бы, и ошибка осталась бы
в одной из них.

```
render → validate → backup → install → reload
```

1. **render** — `deploy/Caddyfile` из текущего checkout'а, адрес сайта
   переписывается на домен сервера. Домен берётся из `DOMAIN`, а если он не
   задан — из `api.env`, по порядку: `PUBLIC_APP_URL`, `PUBLIC_API_URL`,
   `CORS_ORIGINS` (первый origin списка). Ключей три, потому что
   `setup-server.sh` **никогда не перезаписывает существующий `api.env`**: сервер
   живёт с тем шаблоном, с которым его развернули, и `PUBLIC_APP_URL` на нём
   может просто отсутствовать. Именно на этом упал первый деплой синхронизации.
   В лог пишется, из какого ключа взят домен. Значение проверяется регуляркой:
   пробел или фигурная скобка в домене открыли бы второй site-блок, поэтому такое
   отклоняется до рендера. Файл секретов **читается grep/sed, а не `source`**:
   там лежит токен бота, и бэктик в секрете не должен исполниться ради получения
   имени хоста.
2. **validate** — `caddy validate` запускается по **staged**-файлу
   `/srv/shop/caddy/Caddyfile.staged`, то есть **до** того, как тронут рабочий
   конфиг. Это главное свойство схемы: невалидный конфиг стоит проваленного
   деплоя, но никогда — сломанного сервера. Раньше `setup-server.sh` писал `awk`
   прямо в `/etc/caddy/Caddyfile` и валидировал уже результат — битый конфиг
   уничтожал рабочий, и сервер продолжал работать из памяти до первого reload,
   после которого не поднимался.
3. **backup** — вытесняемый конфиг сохраняется в `Caddyfile.rollback` (его
   читает `restore`) и в `Caddyfile.bak.<таймстемп>` для человека. Бэкапов
   хранится 10, дальше старые удаляются: настоящая история — в Git.
4. **install** — `install -o root -g root -m 644` со staged-файла.
5. **reload** — `systemctl reload caddy`.

**Если конфиг не изменился, не происходит ничего.** Обычный деплой не вызывает
ни `validate`, ни `reload`: лишняя перезагрузка процесса, обслуживающего трафик,
— это лишний риск, а изменение конфига благодаря этому видно в логе деплоя как
событие, а не как шум на каждом запуске. Копия для отката при этом всё равно
обновляется — см. ниже.

### Откат конфига

Если релиз не прошёл health check, `deploy.sh` возвращает симлинк на предыдущий
релиз **и** восстанавливает предыдущий Caddyfile. Код и конфиг откатываются
вместе: приложение на старом релизе с конфигом от нового — рассогласование,
которое никому не придёт в голову искать.

`restore` тоже валидирует файл перед установкой: откат, ставящий битый конфиг,
превращает одну проблему в две.

**Копия для отката обновляется и при no-op.** Она обязана содержать конфиг,
который был активен непосредственно перед **этим** деплоем, а у деплоя, ничего
не менявшего в конфиге, такой конфиг тоже есть. Без этого файл хранил бы то, что
вытеснил последний **менявший** конфиг деплой, и провалившийся деплой без правок
конфига откатил бы Caddy на шаг глубже — на конфиг, под которым работающий релиз
никогда не запускался.

### Права sudo

Пользователь `shop` не имеет права писать в `/etc/caddy` напрямую. Вместо этого
`setup-server.sh` выдаёт четыре правила с **фиксированными аргументами и без
wildcard**:

| Команда | Зачем |
| --- | --- |
| `caddy validate --config /srv/shop/caddy/Caddyfile.staged` | запасной путь: обычно валидация проходит без sudo |
| `install -o root -g root -m 644 /srv/shop/caddy/Caddyfile.staged /etc/caddy/Caddyfile` | установить синхронизированный конфиг |
| `install -o root -g root -m 644 /srv/shop/caddy/Caddyfile.rollback /etc/caddy/Caddyfile` | вернуть предыдущий при откате |
| `systemctl reload caddy` | применить установленный конфиг |

Плюс прежние `systemctl restart|status|is-active shop-api`.

Безопасность держится на том, что **пути в правилах литеральные**: право писать
в `/etc/caddy/Caddyfile` нельзя переиспользовать, чтобы записать что-то ещё, а
владельца и режим задаёт само правило. Именно ради этого нужен каталог
`/srv/shop/caddy/` — он принадлежит `shop`, поэтому скрипт готовит файлы без
привилегий, и ни одному правилу не нужен wildcard. Каталог намеренно **не**
внутри `shared/`: тот отдаётся Caddy как `root` для `/uploads/*`, и конфиг рядом
с раздаваемыми файлами — одна опечатка до того, чтобы его можно было скачать.

Правило для `caddy validate` — запасное. Скрипт сначала пробует
валидировать без привилегий и escalate'ит, только если не вышло: `caddy
validate` инициализирует модули из конфига, включая файловый логгер в
`/var/log/caddy`, который принадлежит `caddy:caddy`, — и непривилегированный
запуск может выдать ошибку доступа, неотличимую от «конфиг сломан». На сервере,
где непривилегированный вызов проходит, правило не используется и может быть
удалено.

### Диагностика

```bash
diff /srv/shop/repo/deploy/Caddyfile /etc/caddy/Caddyfile   # разошлись ли
ls -1t /srv/shop/caddy/                                     # staged, rollback, бэкапы
sudo caddy validate --config /etc/caddy/Caddyfile           # валиден ли рабочий
sudo journalctl -u caddy -n 30                              # что сказал сам Caddy
```

Синхронизировать вручную, не выполняя деплой:

```bash
sudo -u shop bash /srv/shop/repo/deploy/sync-caddy.sh apply
sudo -u shop bash /srv/shop/repo/deploy/sync-caddy.sh restore   # вернуть предыдущий
```

Проверить, что `/uploads/*` действительно отдаётся с диска, а не подменяется
SPA-фолбэком (тот самый баг, ради которого всё это сделано):

```bash
curl -sI https://ochkisk.shop/uploads/<имя-файла> | head -3   # ждём image/*, не text/html
curl -so /dev/null -w '%{http_code}\n' https://ochkisk.shop/uploads/nonexistent   # ждём 404
```

`Content-Type: text/html` на существующем файле или `200` на несуществующем
означают, что рабочий конфиг снова разошёлся с репозиторием.

## 7.0. Оплата картой, СБП и криптовалютой (Cashera)

Внешний шлюз: покупатель платит на странице Cashera, а магазин узнаёт результат из
подписанного вебхука. Оплата в рублях, без конвертации — базовая цена товара уже
хранится в копейках, и это же значение уходит в шлюз. Криптовалюта тоже выставляется
в рублях: конвертацию в монету делает Cashera по своему курсу на своей странице.

### Настройка

```bash
sudo -u shop tee -a /srv/shop/shared/api.env >/dev/null <<'EOF'
CASHERA_API_KEY=...
CASHERA_API_SECRET=...
CASHERA_BASE_URL=https://api.cashera.cash/api/v1
CASHERA_PAYMENT_METHOD=sbp
CASHERA_CRYPTO_PAYMENT_METHOD=crypto
EOF
sudo systemctl restart shop-api
```

Права `api.env` — 600, владелец `shop`. Не ослаблять.

Рельс включается только когда заданы **оба** значения: ключ без секрета мог бы
создавать платежи, но не смог бы аутентифицировать вебхук, который сообщает об
оплате, — то есть брать деньги и не узнавать об этом.

`CASHERA_API_SECRET` — только для входящих вебхуков (заголовок `X-Secret`).
Наружу он не отправляется никогда и вырезан из логов в `server.ts`.

### Рельсы: карта и крипто

Один шлюз, два рельса. Покупатель выбирает его в корзине:

- `CASHERA_PAYMENT_METHOD` — код метода для карточного рельса (`sbp`, `card`, …).
- `CASHERA_CRYPTO_PAYMENT_METHOD` — код метода для крипто-рельса. Значение
  `crypto` (по умолчанию) отправляет `payment_method: "crypto"`, и Cashera сама
  показывает доступные монеты и сети на своей странице. Магазин не называет
  конкретную валюту и не хардкодит USDT.

Конкретный набор монет за `crypto` определяется **настройками merchant в кабинете
Cashera**, а не этим кодом. Если метод не включён в кабинете, Cashera вернёт `422`.

Пустое значение `CASHERA_CRYPTO_PAYMENT_METHOD=""` включает общую платёжную форму
Cashera: `payment_method` полностью исключается из JSON, и покупатель выбирает из
всех методов, подключённых merchant'у (карта и СБП рядом с крипто). Это самый
широкий официальный flow, но он не ограничивает покупателя криптой, поэтому по
умолчанию не используется.

### Вебхук

В личном кабинете Cashera указать:

```
https://ochkisk.shop/webhooks/cashera
```

Адрес формируется из `PUBLIC_API_URL` (или `PUBLIC_APP_URL`), поэтому в
`callback_url` он попадает автоматически. Без публичного адреса создание платежа
отклоняется: шлюзу некуда сообщать результат.

Вебхук подтверждает любое событие `2xx`, но обрабатывает только
`transaction.status_updated`. Прочие типы (`webhook.test`, `payout.*`,
`subscription.*`) подтверждаются и игнорируются: по документации Cashera ответ `4xx`
трактуется как ошибка конфигурации и останавливает повторы.

### Проверка

`/health` показывает:

```json
"cashera": { "enabled": true, "paymentMethod": "sbp", "callbackConfigured": true }
```

`GET /api/payment-options` возвращает `cardAvailable: true` — по этому полю
Mini App показывает способ оплаты. Крипто-рельс использует тот же флаг: это рельс
Cashera, а не отдельный шлюз.

### Поток оплаты

```
Order (currency=RUB)
  → POST /integration/transactions   (external_id = ord_<orderId>)
  → payment_url
  → покупатель платит на странице Cashera
  → POST /webhooks/cashera           (X-Api-Key + X-Secret)
      аутентификация (constant-time)
      дедупликация по (uuid, status)
      сверка суммы и валюты с заказом
      только status=paid → markOrderPaid() → ключ → уведомление в чат
```

Важное: **возврат на `/pay/ok` не является подтверждением оплаты.** Это только
навигация — URL может открыть кто угодно. Источник истины — вебхук либо явная
проверка `POST /api/orders/:id/cashera-payment/refresh`, которая перечитывает
статус у шлюза (путь восстановления, если вебхук не пришёл).

Ни один статус кроме `paid` заказ не оплачивает. `refunded` и `chargeback`
фиксируются, но выдачу автоматически не отменяют — это решение человека.

### Локальная разработка

Нужен публичный HTTPS для вебхука: поднять туннель на порт 8080 и указать его в
`PUBLIC_API_URL`, затем прописать этот адрес в кабинете Cashera. Без вебхука
статус можно получить кнопкой «Я оплатил — проверить» в Mini App.

## 7.1. Включение оплаты USDT (BEP20)

По умолчанию выключена: `/health` показывает `crypto.enabled: false`, и API
отказывается создавать USDT-платежи. Включение — три шага.

### Шаг 1. Сгенерировать ключи — НА СВОЕЙ МАШИНЕ, не на сервере

```bash
npm run crypto:keygen -w @shop/api
```

Выводит две части. Разница между ними — это вся модель безопасности:

| Что | Куда | Почему |
| --- | --- | --- |
| **Мнемоника** (24 слова) | офлайн-менеджер паролей или бумага | единственное, чем можно потратить средства |
| **`CRYPTO_DEPOSIT_XPUB`** | `api.env` на сервере | выводит адреса и **не может** подписывать |

Мнемоника никуда не записывается: ни в БД, ни в файл, ни в лог. Она существует
только в памяти процесса и в скроллбеке терминала — поэтому и генерировать её
надо не по SSH на проде: мнемоника в истории команд сервера — это мнемоника в
бэкапе.

Магазин **принимает платежи без мнемоники**. Она понадобится только будущему
sweep-компоненту, который выводит средства в казну.

Команда печатает первые три адреса. **Импортируйте мнемонику в кошелёк и
сверьте, что он показывает те же адреса, до приёма реальных платежей**:
расхождение означает, что деньги уйдут на адреса, ключа к которым нет.

Если xpub нужно получить из уже существующей мнемоники:

```bash
npm run crypto:keygen -w @shop/api -- --xpub
```

### Шаг 2. Прописать на сервере

```bash
sudo -u shop tee -a /srv/shop/shared/api.env >/dev/null <<'EOF'
CRYPTO_PAYMENTS_ENABLED=true
CRYPTO_DEPOSIT_XPUB=xpub...
CRYPTO_DERIVATION_BASE_PATH=m/44'/60'/0'/0
EOF
sudo systemctl restart shop-api
```

Права `api.env` уже 600 и владелец `shop` — не ослабляйте их.

Если случайно вставить `xprv` или мнемонику, процесс **не запустится**:
`config.ts` проверяет это на старте. Веб-процесс не должен иметь права тратить,
и это правило лучше нарушить громко при рестарте, чем тихо в рантайме.

### Шаг 3. Проверить

```bash
# на сервере, от имени shop
cd /srv/shop/current/apps/api && node dist/cli/crypto-check.js
```

Скрипт разделяет три состояния, снаружи выглядящих одинаково: плохой конфиг,
недоступный RPC и декодер, разошедшийся с тем, что отдаёт сеть. Проверяет
доступность обоих эндпоинтов, тег `finalized`, отставание финальности и
декодирует реальные `Transfer`-логи одного блока.

Затем `/health` должен показать `crypto.enabled: true`, `derivationReady: true`
и ненулевой `lastScannedBlock` после первого прохода наблюдателя.

### Первый реальный платёж

Проверяйте малой суммой. Создайте товар с базовой ценой в рублях, оформите
заказ с оплатой USDT, отправьте **точную** показанную сумму в сети BEP20 и
следите за `/health` и вкладкой «Финансы» в режиме управления.

Средства остаются на депозитных адресах: sweep — отдельная фаза. Выдача товара
от него не зависит, но и в казну ничего не переводится автоматически.

## 8. Безопасность стенда

- Порт 8080 закрыт извне, API доступен только через Caddy.
- Заголовки: HSTS, CSP с `frame-ancestors` для доменов Telegram (не `DENY` —
  Mini App живёт в iframe), `nosniff`, скрытый `Server`.
- `index.html` не кешируется, `/assets/*` — иммутабельно на год.
- systemd-юнит ужат: `ProtectSystem=strict`, `NoNewPrivileges`,
  единственный writable путь — `/srv/shop/shared`.
- `api.env` с правами 600, принадлежит `shop`; systemd читает его сам.
- Права sudo у `shop` — семь команд с фиксированными аргументами, без wildcard
  (раздел 6). Записать в `/etc/caddy/Caddyfile` можно только из двух заранее
  заданных файлов.

## 9. Ограничения текущего стенда

- **SQLite**, одна машина, без репликации. Для теста нормально, под нагрузку —
  переход на Postgres (см. ниже).
- **Автобэкапов нет**: команда из раздела 5 при необходимости кладётся в cron.
- Артефакт вырос до ~100 МБ и **привязан к платформе**: собран под Linux x64 и
  конкретный мажор Node. Это цена за то, что сервер не запускает `npm ci` —
  памяти на него не хватает. См. раздел 2.
- **Диск 9.7 ГБ — узкое место.** Релиз с `node_modules` занимает ~400 МБ,
  поэтому хранится всего два. Держите свободными хотя бы 1 ГБ: `deploy.sh`
  требует пятикратный размер архива и иначе не начинает распаковку.
- Мажор Node в CI и на сервере обязан совпадать. Меняете один — меняйте оба:
  `env.NODE_VERSION` в workflow и `NODE_MAJOR` в `setup-server.sh`.

### Диагностика деплоя

| Симптом | Причина и что делать |
| --- | --- |
| `artifact not found` | либо CI не догрузил файл (проверьте job `deploy` и права на `/srv/shop/incoming`), либо вы запускаете `deploy.sh` повторно после того, как успешный деплой удалил архив — перезапустите workflow |
| `artifact checksum mismatch` | обрыв передачи; перезапустите workflow |
| `artifact.json is missing` | загружен не тот архив |
| `not enough free disk space to unpack this release` | диск полон; релиз не ставился, сайт работает. Расчистка — раздел 5, «Место на диске» |
| `could not unpack the artifact (out of disk space?)` | `tar` упал на середине; каталог релиза удалён автоматически, освободите место и запустите деплой снова |
| `No space left on device` в логах CI-шага «Install the release» | то же самое; после фикса чистка идёт до распаковки, поэтому обычно достаточно перезапустить workflow |
| `artifact was built on Node X but this host runs Y` | мажоры CI и сервера разошлись; выровняйте `env.NODE_VERSION` и `NODE_MAJOR` и пересоберите |
| `artifact was built for win32/x64 but this host is linux/x64` | артефакт собран локально не на Linux; собирайте в CI |
| `Killed  npm ci` | старый артефакт без зависимостей на слабой машине; пересоберите на актуальном коммите |
| `tsx: not found` при `npm run db:seed` на сервере | dev-скрипт в production-дереве; запускайте `node --env-file=/srv/shop/shared/api.env dist/cli/seed.js` |
| `Cannot find module .../dist/cli/seed.js` | релиз собран до переноса скриптов в `src/cli`; задеплойте актуальный `main` |
| `the SQLite driver did not load` | бинарник собран под другой ABI/платформу; проверьте `nodeMajor` и `platform` в `artifact.json` |
| `deploy rolled back` | сайт уже вернулся на прошлый релиз; причина в `journalctl -u shop-api -n 50` |
| `Caddy config sync failed` | деплой остановлен **до** переключения симлинка, работает прежний релиз, `/etc/caddy/Caddyfile` не изменён. Причина в выводе выше: невалидный `deploy/Caddyfile`, недостающее правило sudo или недоступный домен |
| `could not determine the domain` | в `api.env` нет ни `PUBLIC_APP_URL`, ни `PUBLIC_API_URL`, ни `CORS_ORIGINS`. Допишите любой из них или задайте домен явно: `DOMAIN=ochkisk.shop bash /srv/shop/repo/deploy/sync-caddy.sh apply` |
| `the rendered Caddy config is invalid` | ошибка в `deploy/Caddyfile`; рабочий конфиг не тронут, сайт работает. Проверьте локально: `caddy validate --config deploy/Caddyfile` |
| `could not install … to /etc/caddy/Caddyfile` | правило sudo не совпало дословно (обычно после смены `APP_ROOT` или пути к `install`); перезапустите `setup-server.sh` |
| `caddy reload failed` | конфиг валиден и уже на диске, но процесс работает со старым; `journalctl -u caddy -n 30`, затем `systemctl reload caddy` вручную |
| картинки `/uploads/*` отдаются как `index.html` | рабочий конфиг разошёлся с репозиторием; `diff /srv/shop/repo/deploy/Caddyfile /etc/caddy/Caddyfile` и `sync-caddy.sh apply` (раздел 6) |

### Переход на PostgreSQL

1. `apps/api/prisma/schema.prisma`: `provider = "postgresql"`.
2. `apps/api/src/db.ts` и `prisma.config.ts`: адаптер `@prisma/adapter-pg`.
3. `DATABASE_URL` — строка подключения, затем `npx prisma migrate dev`.

Схема не использует SQLite-специфичных типов, поэтому модели переносятся
без изменений. Бонус: исчезает нативный модуль SQLite, а вместе с ним и
привязка артефакта к платформе — один архив станет годен для любой машины с
подходящим мажором Node.
